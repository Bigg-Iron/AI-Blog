The AI Agent Stack Explained:
Tools, Skills, Plugins, MCP & A2A

Lorenzo Bartolo · 9 May 2026 · 10 min read

If you've spent any time working with AI agents, you've almost certainly run into a wall of overlapping terminology. Tools. Skills. Plugins. MCP servers. A2A protocol. These words get used interchangeably in blog posts and documentation, but they describe fundamentally different things. Understanding the distinction isn't just semantic pedantry — it's the difference between building systems that scale and bolting things together that break.

This post breaks down each layer of the AI agent stack from the ground up, and then zooms in on Google's Agent-to-Agent (A2A) protocol, which is quietly becoming one of the most important infrastructure standards in the industry.

Layer 1 Tools The atomic unit of agent action
Layer 2 MCP Servers Toolboxes — coherent bundles of tools
Layer 3 Skills Encoded expertise and domain judgment
Layer 4 Plugins Packaged, distributable workflows
Layer 5 Agents & Orchestration LLM + tools + skills, working toward goals
Protocol A2A Cross-agent, cross-org communication

Layer 1: Tools — The Atomic Unit of Agent Action

A tool is the most primitive building block in an AI agent system. It is a single callable function — a named action with defined inputs and outputs that an AI model can invoke mid-reasoning.

Some examples to make this concrete:

  • search_web(query: string) — returns search results
  • read_file(path: string) — returns file contents
  • execute_bash(command: string) — runs a shell command
  • take_screenshot() — captures the current screen

When an LLM has access to tools, it doesn't just generate text — it generates decisions. The model reasons about what needs to happen, selects the right tool, provides the required inputs, observes the output, and continues reasoning. This loop — reason, act, observe, repeat — is the foundation of agentic behaviour.

The description matters more than you'd think. Tools are defined by a name, a description, and a JSON schema for their inputs. The description is how the model understands what a tool does and when to use it. A poorly described tool is nearly as useless as no tool at all.

Tool/function calling is now supported by every major LLM provider — OpenAI, Anthropic, Google, Mistral, and others. The underlying pattern is standardised; the exact API shape varies slightly between providers.

Layer 2: MCP Servers — The Toolbox

A single tool is useful. Thirty related tools delivered as a coherent unit are a capability.

MCP (Model Context Protocol) is an open standard, originally developed by Anthropic and now widely adopted across the industry, that defines how tools are packaged, exposed, and consumed by AI agents. An MCP server is essentially a toolbox: a running process that declares a set of related tools and handles execution when an agent calls them.

Consider a GitHub MCP server. Rather than a developer wiring up each GitHub API call individually, they install the GitHub MCP server and the agent gains the full suite in one step — tools like list_pull_requests, create_branch, get_file_contents, add_issue_comment, and merge_pull_request.

The key insight is interoperability. Because the protocol is standardised, an MCP server built for Claude will work with Gemini, GPT-4, Copilot, and any other MCP-compatible runtime. As of 2026, MCP is supported natively by Anthropic, OpenAI, Microsoft, and Google — and by most major agent frameworks including LangGraph, CrewAI, and AutoGen. Investment in MCP servers is investment that travels.

Traditional API Integration MCP Server
Wiring Per-application, per-LLM Write once, works everywhere
Discovery None — hardcoded Agents discover tools dynamically
Portability Tied to a specific implementation Any MCP-compatible runtime
Maintenance Breaks when LLM provider changes Isolated from LLM changes

Layer 3: Skills — Encoded Expertise

Tools give an agent capability. Skills give an agent judgment.

A skill is a set of instructions that tells an agent how to approach a specific class of task well. It's not a new tool — it's accumulated best practice, workflow logic, and domain expertise delivered as a structured prompt or instruction document.

Think of the difference between handing someone a hammer (a tool) versus teaching them carpentry (a skill). The skill encodes: what order to do things in, what to watch out for, what a good outcome looks like, and how to handle edge cases.

An example: a skill for generating financial tear sheets doesn't give Claude new API access. It tells Claude which data points matter, how to structure the analysis, what financial ratios to calculate and why, and how to present findings for a specific audience. Strip out that skill, and the same tools produce generic, shallow output.

Skills are currently proprietary. Anthropic has a skill format for Claude/Cowork, OpenAI has an equivalent for GPTs, Google has Gems. There is no cross-LLM standard for skills at the time of writing — which means they're also where platforms differentiate.

Layer 4: Plugins — The Distribution Unit

If tools are ingredients and skills are recipes, plugins are the packaged product.

A plugin bundles together:

  • One or more MCP servers (tools and their implementations)
  • Skills (instructions for how to use those tools effectively)
  • Configuration, authentication flows, and metadata

Plugins are the unit you install, share, and distribute. A data analytics plugin might include an MCP server connecting to a financial data API, a skill for building peer comparison models, another skill for generating earnings previews, and all the OAuth config to authenticate with the data provider. One install, full workflow.

This matters because the real value in an agent system often isn't in any individual tool — it's in the combination of tools, the expertise in how to use them together, and the workflow that ties them into something repeatable.

Layer 5: Agents and Orchestration

Stack tools, MCP servers, skills, and plugins together, add a capable LLM, and you have an agent: a system that can reason, plan, take actions, observe outcomes, and work toward goals autonomously.

Multi-agent systems take this further. Rather than one agent doing everything, you have an orchestrator that delegates subtasks to specialist agents, each optimised for a specific domain. A research agent, a coding agent, a writing agent, and a QA agent might all run in parallel — each with their own tools and skills — with the orchestrator stitching their outputs into a coherent result.

This is where the A2A protocol enters.

The A2A Protocol: How Agents Talk to Each Other

MCP solves how an agent connects to tools and data. A2A solves a different problem: how do two agents — potentially built by different companies, running on different LLMs, deployed on different infrastructure — communicate with each other?

Google published the Agent-to-Agent (A2A) protocol in April 2025 and subsequently donated it to the Linux Foundation. It is an open specification for agent interoperability across organisational and technological boundaries.

The Core Problem A2A Solves

Without a standard, agent-to-agent communication is bespoke. If Company A builds an agent on Claude and Company B builds an agent on Gemini, and they want those agents to collaborate on a task, someone has to write custom integration code. That code breaks when either agent changes. It doesn't generalise. It doesn't scale.

A2A creates a common language so any A2A-compliant agent can communicate with any other, regardless of the underlying LLM, framework, or vendor.

How A2A Works

A2A is built on three foundational concepts:

Agent Cards — Every A2A-compliant agent publishes an Agent Card: a JSON document that describes what the agent can do, what inputs it accepts, what outputs it produces, and how to reach it. This is the discovery mechanism. An orchestrator agent looking for help with a specific task queries available Agent Cards to find the right specialist.

Tasks — Communication in A2A is task-oriented. A client agent sends a Task object to a remote agent — a structured request with defined inputs, expected outputs, and a lifecycle (pending → working → completed/failed). For long-running work, both agents stay in sync via status updates throughout. This provides something that informal message-passing doesn't: a shared model of what "done" looks like, and a clear mechanism for handling partial completion, errors, and timeouts.

Transport Layer — A2A runs over HTTPS with JSON-RPC 2.0 as the data format, with Server-Sent Events (SSE) for streaming updates on long-running tasks. A2A agents are reachable over the standard web — no proprietary networking stack required.

A2A vs. MCP: Complementary, Not Competing

This is a common point of confusion. The clean distinction:

MCP A2A
What it connects Agent ↔ Tools / Data Agent ↔ Agent
Scope Within an agent system Across agent systems and organisations
Analogy A worker's toolbelt A contractor hiring another contractor
Governed by Anthropic (open spec) Linux Foundation

In a mature multi-agent architecture, both are present. An agent uses MCP to reach its own tools and data sources. It uses A2A to delegate work to other agents — including agents it didn't build and doesn't control.

2026 Adoption Status

The adoption curve has been steep. As of early 2026, more than 150 organisations support A2A, including Google, Microsoft, AWS, Salesforce, SAP, ServiceNow, Workday, and IBM. Major cloud platforms have integrated it natively: Azure AI Foundry treats A2A as a first-class citizen for multi-agent deployments, Amazon Bedrock AgentCore offers native A2A support, and Google Cloud has deep integration across Vertex AI and Workspace agents.

This breadth of adoption within roughly a year of publication is significant. It suggests A2A is winning the interoperability standards race — which means building against it is a reasonable bet for production systems.

How It All Fits Together: A Worked Example

Say you're building a competitive intelligence system. Here's how the full stack comes together:

Tools handle the primitives: search the web, scrape a URL, read a file, write to a database.

MCP servers bundle those tools into coherent capabilities: a web research MCP, a document processing MCP, a CRM integration MCP.

Skills encode the expertise: how to structure a competitive analysis, what signals to weight, how to present findings for an executive audience.

Plugins package MCP servers and skills into installable units your team can deploy without rebuilding the workflow from scratch.

Agents use plugins and tools to do the actual work — a research agent gathers data, an analysis agent synthesises it, a writing agent produces the deliverable.

A2A lets your internal orchestrator delegate the "research public filings for Company X" subtask to a specialist financial agent running on a different system — maybe a compliance-approved agent your legal team controls, or a third-party data provider's agent accessed as a service.

MCP is what each agent uses to reach its own tools. A2A is what agents use to reach each other.

What's Still Evolving

Skills remain proprietary. There's no cross-LLM standard for skills. A skill built for Claude won't run on Gemini. This is the layer most in need of standardisation and the one least likely to get it soon — it's where platforms differentiate.

Agent identity and trust are unsolved. A2A defines how agents communicate, but the question of how an orchestrator verifies it's talking to the agent it thinks it is — and what permissions that agent should have — is still being worked out. Agent Cards can be spoofed; there's no PKI-equivalent for agent identity yet.

Observability is immature. In a multi-agent system with ten agents calling each other via A2A and each using MCP tools, tracing a failure back to its source is genuinely hard. Tooling for this is improving but not yet at the level of maturity that engineers expect from distributed systems.

The Bottom Line

The AI agent stack is converging on a two-protocol world: MCP for tool connectivity, A2A for agent interoperability. Both are open standards with broad industry adoption. Both are reasonable foundations to build on today.

Above that protocol layer, tools and skills remain the unit of agent capability — and plugins are how you package and distribute workflows worth reusing. The vocabulary is settling. The underlying architecture is real, and it's being deployed in production at scale.

Invest in MCP servers (your work is portable), understand A2A deeply (it's where multi-agent systems are heading), and treat skills as your competitive moat — they're where domain expertise lives.
